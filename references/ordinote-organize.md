# 笔记文件夹结构整理

## 功能定义

对用户指定的文件夹，本模块包含两个并行子功能：

1. **结构检查与初始化（structure）**：确认哪个文件夹是根 Area 主要文件夹，并确认其下的文件夹为 Project 附属文件夹；确认该主要文件夹所属的 Area 领域以及该领域的分类是否合理（若不合理，仅给出建议，不做任何修改）；阶段一按标准结构自动新建全部所需文件夹（不移动任何文件），并给出归类意见
2. **内容聚类整理（organize）**：对主要项目下的附属项目（Project）进行聚类、分类、整理，重点检查"项目文件夹或其余文件"部分的内容，给出分类与规划意见

两个子功能均采用两阶段流程：structure 在阶段一直接新建文件夹、不移动文件；两者的文件移动一律在用户明确确认后执行。

## 功能选择

- 用户要求确认 Area / Project 归属、评估领域分类、按标准结构新建文件夹或初始化项目结构 → 结构检查与初始化（structure）
- 用户要求对附属项目、散落文件进行聚类、分类、整理 → 内容聚类整理（organize）
- 用户笼统要求"整理这个文件夹"且目标结构尚未建立 → 先执行 structure 的检查与文件夹新建，再按需执行 organize；两者给出的方案可合并展示，文件移动均须用户确认后执行

## 项目组织方法论（两个子功能共用的判断基础）

参考 PARA 思想，从大到小的层级是：Area → Projects → files/docs

- **Area**：一个长期致力于其中的领域，只要用户还感兴趣，它就一直存在（如哲学或精神分析本身）
- **Project**：一个更为具体的组织，有明确的目标（如"复习总结完弗洛伊德的某一本书，甚至是一整个时期的书"）
- **Files/Docs**：最小的执行和完成单元

### Area 大小的划分原则

一个主要项目就是一个 Area。要合适地划分一个 Area 的大小，不能太大也不能太小：

- 合适的大小：如狭义的精神分析流派（弗洛伊德-拉康-齐泽克）、德国古典哲学
- 过大的大小：如直接分类为"哲学"、"近现代哲学"
- 过小的大小：如不做过于深入的研究时，把单个人的思想单独拎出来作为一个 Area（如"萨特"）

### 标准 Area 结构（主要项目）

```text
Area/
├── ai/               # 供 llm 使用的文件夹
│   ├── context/          # 提取过便于 llm 阅读的文件（.txt 或 .md）
│   ├── ai_outputs/       # llm 输出的未经审核的内容，经仔细审核的放入 resources 文件夹
│   └── 其余文件夹/         # 按需添加
├── archives/         # 已归档内容、已结束项目
├── originals/        # 原始文件档案源头（如原始书籍扫描 pdf）
├── inbox/            # 输入的（未整理）资料
├── images/           # 图片
├── resources/        # 常用资源
├── 附属项目文件夹、其余文件
├── README.md         # 如该项目需要分享，则这个文件是给别人读的
└── ROADMAP.md        # 给自己看的待办事项
```

### 标准 Project 结构（附属项目）

一个附属项目就是一个 Project。附属项目不设立 ai/、archives/、originals/、inbox/ 等部分文件夹，这部分内容应当全部放在附属项目所属的主要项目下，以防止附属项目变得过于臃肿。

```text
Project/
├── images/           # 图片
├── resources/        # 该项目的常用资源
├── 项目文件夹或其余文件
├── README.md         # 如该项目需要分享，则这个文件是给别人读的
└── ROADMAP.md        # 给自己看的待办事项
```

## 功能一：结构检查与初始化（structure）

### 阶段一：检查、自动新建文件夹与方案生成（只新建文件夹，不移动任何文件）

#### 1. 确认 Area 与 Project 归属

- 扫描目标文件夹（**递归，包含子文件夹中的文件**）；非 markdown 文件（如 pdf、图片等）只记录文件名，不读取内容
- 确认哪个文件夹是根 Area 主要文件夹，并确认该主要文件夹之下的文件夹为 Project 附属文件夹
- 仅凭文件夹名与文件名不足以判断时，读取相关文件的开头部分辅助判断，无需通读全文
- 若无法确定目标文件夹的归属（Area 主要文件夹还是 Project 附属文件夹），先向用户确认角色，确认后再执行后续步骤

#### 2. 评估 Area 领域分类

- 确认该主要文件夹所属的 Area 领域
- 按"Area 大小的划分原则"评估该领域的分类是否合理
- 分类不合理（过大或过小）时，给出调整建议（如拆分、合并、调整层级）
- **评估只给出建议，不得做任何实际修改**

#### 3. 按标准结构自动新建文件夹

- 对照"标准 Area 结构"与"标准 Project 结构"，列出主要项目与各附属项目缺失的文件夹清单，并**直接新建，无需等待用户确认**
  - Area 层级：ai/（含 ai/context/、ai/ai_outputs/）、archives/、originals/、inbox/、images/、resources/
  - Project 层级：images/、resources/
- 已存在的同名文件夹一律保留，不重复新建、不覆盖、不删除其中内容
- 只新建文件夹；README.md、ROADMAP.md 等属于文件，不在自动新建范围内，可在方案中提示用户按需创建
- **本步骤不得移动、重命名、删除、修改任何文件**

#### 4. 生成方案

- 报告本次已新建的文件夹清单及各自用途
- 给出散落文件的归类意见（是否移动由用户决定，在阶段二执行）
- 给出领域分类评估结论与调整建议（仅建议）
- 现有结构原本已完整时，如实反馈，不强行为之新建文件夹
- 归类不确定的文件，单独列出并说明疑虑

方案内容必须包括：

- **结构树**：结构化后的目录树，标注本次新建项；如给出文件移动建议，一并标注待移动项
- **新建文件夹清单**：本次已新建的文件夹及用途
- **归类意见**：散落文件的建议去向（文件移动须经用户确认后执行）
- **领域分类评估**：结论与调整建议（如有）

**此阶段只新建文件夹，不得移动、重命名、删除、修改任何文件！**

### 阶段二：文件移动（仅在用户确认后；用户不需要移动文件时直接跳过）

- **触发条件**：用户明确表示同意归类意见并要求移动文件（如"按方案移动"、"可以，执行吧"等）
- 用户对方案提出修改意见时，先修改方案并再次展示，直到用户确认
- 文件夹已在阶段一新建完成；如用户对结构另有要求，先按要求调整文件夹，再移动文件
- 执行内容：按方案将文件移动到对应文件夹
- 完成后向用户汇报：移动了哪些文件、最终的目录结构

## 功能二：内容聚类整理（organize）

### 适用范围

对主要项目下的附属项目（Project）进行聚类、分类、整理。**重点检查"项目文件夹或其余文件"部分的内容**：各附属项目的归属是否合理、项目内的文件夹与散落文件应如何聚类分类，给出分类与规划意见。

标准结构文件夹（ai/、archives/、originals/、inbox/、images/、resources/ 等）的建立与 Area 领域分类的评估由功能一负责，本功能不涉及。

### 阶段一：分析与方案生成（不移动任何文件）

#### 1. 扫描文件清单

- 列出目标文件夹下的所有文件和子文件夹（**递归，包含子文件夹中的文件**）
- 非 markdown 文件（如 pdf、图片等）只记录文件名，不读取内容

#### 2. 判断每个文件的内容

- **原则：能根据文件名判断大致内容的，一律不读取文件内容**
  - 文件名清晰的（如 `意识理论笔记.md`、`2026-03-05课堂笔记.md`）→ 仅凭文件名归类
- **仅当文件名无法判断内容时才读取该文件**：
  - 文件名含糊的（如 `未命名.md`、`笔记1.md`、`新建文档.md` 等）
  - 读取文件开头部分（标题、前几段）确定主题即可，无需通读全文
- **判断依据不足时，宁可读取文件，也不要凭猜测归类**

#### 3. 生成整理方案

基于以下三大原则设计目标文件夹结构：

1. **逻辑归属**：按主题、项目、课程、时间等笔记的内在逻辑划分归属
2. **聚类**：内容相近、主题相关的笔记聚合到同一文件夹；同一主题下数量多的可再细分
3. **合理的文件夹嵌套**：
   - 层级不宜过深，一般不超过 3 层
   - 避免"一个文件夹里只有一个文件"的过度细分
   - 避免把主题不相关的文件塞进同一文件夹

方案内容必须包括：
- **目标文件夹结构树**：用代码块画出整理后的目录树，并对各文件夹的用途做简要说明
- **文件移动对照表**：每个文件从原位置移动到新位置
- 归类不确定的文件，在方案中单独列出并说明疑虑

**此阶段只输出方案，不得移动、重命名、删除任何文件！**

### 阶段二：执行整理（仅在用户确认后）

- **触发条件**：用户明确表示同意方案（如"按方案整理"、"可以，执行吧"等）
- 用户对方案提出修改意见时，先修改方案并再次展示，直到用户确认
- 执行内容：按方案将文件移动到对应文件夹
- 完成后向用户汇报：移动了哪些文件、最终的目录结构

## 安全约束（最重要！！）

<important>

1. **允许的操作只有新建文件夹与移动文件；不允许删除文件，不允许修改任何文件的内容**
2. **不允许重命名文件和文件夹**（除非方案中明确写出且用户已确认）
3. **文件夹新建按标准结构在阶段一直接执行，无需等待确认；文件移动必须在用户明确确认（阶段二）后执行，确认前不得移动任何文件**
4. **自动新建的范围仅限于标准结构所要求的文件夹；超出标准结构的调整（拆分、合并、新建其他文件夹）仍须先出方案并经用户确认**
5. **Area 领域分类的评估结论与调整建议仅供参考，不得据此执行拆分、合并、改名等任何实际改动**（如用户明确要求采纳某条建议，仍需另行给出方案并经用户确认）

</important>

## 注意事项

- **若存在无法归类的零散文件，可在方案中建议一个"待归类"或"其他"文件夹，并说明理由**
- **若目标文件夹下文件很少（如少于 5 个）或现有结构已经很清晰，可向用户反馈"当前结构已较合理"，不强行为之设计新结构**
- 执行过程中遇到文件名冲突（目标位置已存在同名文件）时，暂停并向用户反馈，不得擅自覆盖或改名
- **如果在分析过程中发现任何问题（如大量与笔记无关的文件等），请及时向用户反馈**
- 目录结构一经建立即应保持稳定，不提倡频繁重构；方案设计以长期稳定为目标，重点应放在内容本身
